# Hatchet Sticky Worker Assignment with a 3-Step DAG (Python) ## Background Hatchet supports **sticky assignment**, which keeps all tasks within a workflow on the same worker for the duration of the workflow run. This is useful when tasks share expensive local state (model weights, caches, sessions). In this task you will demonstrate this feature using the official `hatchet-sdk` Python package against **Hatchet Cloud** (no self-hosting). Your job is to build a Python project that: 1. Defines a single Hatchet **DAG workflow** with **three sequentially-dependent tasks** `step_a -> step_b -> step_c` where the workflow is configured with `StickyStrategy.SOFT` (or `HARD`). 2. Starts **two long-running workers** as separate OS processes in the same container (different process IDs, both connected to the same Hatchet Cloud tenant) so the scheduler actually has a choice between them. 3. Triggers the workflow exactly once and waits for it to finish. 4. Records, from inside each task body, the executing worker's identifying information (hostname and a unique `WORKER_ID` env variable that distinguishes the two worker processes) to a shared log file. 5. After the workflow completes, writes a small JSON summary file that lists the worker ids that ran each step. The verifier will inspect the log file and the JSON summary and confirm that **sticky assignment was honored** — i.e. all three steps executed on the **same** `WORKER_ID`. ## Requirements - Use the official `hatchet-sdk` Python package. - Use **Hatchet Cloud only**. Authenticate with the `HATCHET_CLIENT_TOKEN` already present in the environment. Do **not** override the server address; let the SDK use its default. - Define a DAG workflow named `sticky-dag-${run-id}` (with `run-id` read from the `ZEALT_RUN_ID` environment variable, so concurrent trials do not collide) configured with `sticky=StickyStrategy.SOFT`. - The workflow must contain **three tasks** named `step_a`, `step_b`, and `step_c` with the dependency chain `step_a -> step_b -> step_c` (each subsequent task lists the previous one as its parent). - Inside each task body: - Read the worker identity from the `WORKER_ID` environment variable. - Read the container hostname with `socket.gethostname()`. - Append a single line to `/tmp/run_steps.log` in the exact format: `step=<step_name> worker_id=<WORKER_ID> hostname=<hostname> pid=<pid>` - Return `{"worker_id": <WORKER_ID>}` as the task output so downstream steps can consume it. - Start **two** worker processes concurrently from the runner. Each worker process: - Must run in its own OS process (different PIDs). - Must be started with a different `WORKER_ID` value (e.g. `worker-A-${run-id}` and `worker-B-${run-id}`). - Must register the same DAG workflow and be eligible to execute any of the three steps. - Once both workers are ready, the runner triggers the workflow **exactly once** and waits for it to complete. - After the workflow finishes, the runner writes `/tmp/result.json` containing: ```json {"worker_ids": ["<id-for-step_a>", "<id-for-step_b>", "<id-for-step_c>"]} ``` (the values come from the task outputs / the log file). - The runner must terminate both worker processes cleanly before exiting. - The entire end-to-end run must complete in **under 5 minutes** when invoked with the command below. ## Implementation Hints - Read `run-id` from the `ZEALT_RUN_ID` environment variable and append it to the workflow name and worker ids to make the run safe under concurrent trials. - The SDK exposes a `StickyStrategy` enum and a `sticky` parameter on `hatchet.workflow(...)`. Use the **SOFT** variant. - A DAG task with a parent is created with the `parents=[...]` argument on the task decorator. - Use Python's `multiprocessing` (or `subprocess`) to spawn the two worker processes. Each child process should create its own `Hatchet` client, define / register the same workflow, and call `worker.start()` (which blocks). - Use `os.environ["WORKER_ID"]` inside each task body to read the unique worker id; set it via `env` when spawning each subprocess. - To trigger the workflow you can call `workflow.run(...)` (blocking) or `aio_run(...)` from the parent runner process. Make sure both workers are up before triggering. - Make sure to flush / fsync writes to `/tmp/run_steps.log` so the log lines are durable even if a worker is terminated immediately afterwards. - Do not start a Hatchet server or override `HATCHET_CLIENT_HOST` — the SDK's default points to Hatchet Cloud. ## Acceptance Criteria - Project path: `/home/user/myproject` - Entrypoint: `Command: python3 /home/user/myproject/run.py` - The command must exit with status `0` within 5 minutes. - Log file: `/tmp/run_steps.log` - Must contain exactly **three** lines, one per step. - Every line must match the format: `step=<step_name> worker_id=<worker_id> hostname=<hostname> pid=<pid>`. - The three `step` values must be exactly `step_a`, `step_b`, `step_c` (each appearing at least once). - The `worker_id` value on every line must be **identical** (sticky assignment honored). - Result file: `/tmp/result.json` - Must be valid JSON with the shape `{"worker_ids": ["<id_a>", "<id_b>", "<id_c>"]}`. - All three list entries must be equal to each other and equal to the `worker_id` value seen in `/tmp/run_steps.log`. - The shared `worker_id` must be one of the two ids that were spawned (i.e. it must follow the pattern `worker-A-${run-id}` or `worker-B-${run-id}`). - The implementation must use `sticky=StickyStrategy.SOFT` (or HARD) on the workflow declaration. The verifier will grep the project source for this. - The implementation must spawn **two** worker processes (verifier will grep the source for evidence of spawning two distinct workers with distinct `WORKER_ID` values).
