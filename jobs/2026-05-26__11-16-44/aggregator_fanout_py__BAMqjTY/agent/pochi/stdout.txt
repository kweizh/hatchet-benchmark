# Document-Processing Fan-out + Aggregate DAG with Hatchet Python SDK ## Background You will build a multi-stage Hatchet pipeline using the Python SDK (`hatchet-sdk`) that combines a **declarative DAG** with **runtime child-spawning**, modeling the classic document-processing fan-out + aggregate pattern. A single Hatchet DAG workflow drives three sequential stages. The middle stage runs a dynamic fan-out by spawning a separate child workflow once per input URL (the number of children is determined at runtime by the upstream task's output, not hardcoded). The final stage reads the fan-out result through the DAG's `ctx.task_output(...)` API and produces an aggregated summary. Hatchet Cloud is already provisioned and the worker authentication token is provided via the `HATCHET_CLIENT_TOKEN` environment variable. You do NOT need to configure a server URL — the Python SDK targets Hatchet Cloud by default. ## Requirements * Use the `hatchet-sdk` Python package against real Hatchet Cloud (no mocking, no fake in-process replacement). * Define a Hatchet DAG workflow named `doc_pipeline` containing **exactly three tasks** with the following names and parent relationships: * `prepare` — no parents. * `scrape_all` — parents = `[prepare]`. * `aggregate` — parents = `[scrape_all]`. * Define a **separate child Hatchet workflow** named `scrape_one` that processes one URL at a time. It must be registered on the worker as its own workflow (NOT defined as a task inside the `doc_pipeline` DAG). * Task contracts: * `prepare` returns a JSON-serializable object containing the field `urls` set to the hard-coded list of three strings: `["https://example.com/a", "/b", "/c"]` (these three string values exactly — do not normalize or expand them). * `scrape_one` accepts an input with a string field `url` and returns a JSON-serializable object containing the fields `url` (the same input URL) and `length` set to `len(url) * 7`. URLs are NOT actually fetched — `len(url) * 7` is the deterministic simulation of "scraped page length". * `scrape_all` reads the `urls` list from the upstream `prepare` task's output, then **dynamically spawns one `scrape_one` child workflow per URL at runtime** (the number of children must be determined by the runtime length of `urls`, not hardcoded). Use Hatchet's Python child-spawning bulk API — specifically `scrape_one.aio_run_many(...)` (with `scrape_one.create_bulk_run_item(...)` per URL) — to fan out and gather the child outputs in one call. `scrape_all` must return a JSON-serializable object containing the field `pages`, whose value is a list of `{"url": <str>, "length": <int>}` objects — one per child run. * `aggregate` reads the `pages` list from the upstream `scrape_all` task's output via `ctx.task_output(scrape_all)` and returns a JSON-serializable object containing exactly two fields: `total_length` (the integer sum of all `length` values in `pages`) and `count` (the integer number of pages). * Register BOTH the `doc_pipeline` DAG and the `scrape_one` child workflow on a single Hatchet worker. Start the worker (in the background — e.g., a background thread or subprocess) before triggering the pipeline. * Trigger the `doc_pipeline` DAG exactly once. Wait for the run to complete, then write the `aggregate` task's final output to `/tmp/result.json` as valid UTF-8 JSON (e.g., via `json.dump`). ## Implementation Hints * Install the `hatchet-sdk` Python package. The SDK reads `HATCHET_CLIENT_TOKEN` automatically; no extra client configuration is needed. * Combine `hatchet.workflow(name="...")` to declare a DAG with `@<workflow>.task(...)` (and the `parents=[...]` kwarg) to declare task dependencies. This is the **DAG** primitive — distinct from a standalone `@hatchet.task(...)`. * The child `scrape_one` must be its **own** workflow (e.g., a separate `hatchet.workflow(name="scrape_one")` with a single task, or an `@hatchet.task(name="scrape_one")` standalone task) so that you can invoke it as a child runnable via `.aio_run_many(...)`. Do NOT make `scrape_one` a task inside the `doc_pipeline` DAG. * Inside `scrape_all`, build the bulk inputs with `scrape_one.create_bulk_run_item(input=...)` per URL, then `await scrape_one.aio_run_many([...])` to fan out and gather results in one network round-trip. * The `scrape_all` task body MUST be `async def` so you can `await` the bulk run. * Use `ctx.task_output(<task_reference>)` inside `aggregate` to retrieve `scrape_all`'s output — do NOT recompute or re-spawn anything in `aggregate`. * Start the worker with `hatchet.worker("...", workflows=[doc_pipeline, scrape_one])` and run it in the background so the trigger script can complete the run. Both the DAG workflow and the child workflow MUST be registered on the same worker. * Trigger the DAG via Hatchet (e.g., `doc_pipeline.run(...)` or `await doc_pipeline.aio_run(...)`) — do NOT call the task functions directly as plain Python functions. * The DAG takes no meaningful input; an empty input is fine. * After the run completes, persist the aggregate output as a JSON object to `/tmp/result.json`. ## Acceptance Criteria * Project path: /home/user/myproject * Output file: /tmp/result.json * The `hatchet-sdk` Python package is used; Hatchet is not mocked. * A Hatchet worker that registers BOTH the `doc_pipeline` DAG workflow AND the `scrape_one` child workflow is started against Hatchet Cloud using the `HATCHET_CLIENT_TOKEN` environment variable. * The `doc_pipeline` DAG workflow is triggered exactly once, with the topology `prepare -> scrape_all -> aggregate` (where `scrape_all` parent is `[prepare]` and `aggregate` parent is `[scrape_all]`). * The fan-out in `scrape_all` is implemented via Hatchet child-spawning of the `scrape_one` workflow at runtime (one child per URL produced by `prepare`); the number of children must be derived from the upstream output, not hardcoded. * `/tmp/result.json` MUST exist and contain a JSON object with both keys `total_length` (integer) and `count` (integer).
