## Design

### Workflow definition (inside each worker subprocess)
```
sticky-dag-<ZEALT_RUN_ID>   sticky=StickyStrategy.SOFT
  step_a  ──►  step_b  ──►  step_c
```
Each task returns `{"worker_id": <WORKER_ID>}` and appends one line to `/tmp/run_steps.log`:
```
step=<name> worker_id=<WORKER_ID> hostname=<hostname> pid=<pid>
```

### Process topology
| Process | Role | `WORKER_ID` |
|---------|------|-------------|
| Main (runner) | triggers workflow, writes result | — |
| Child A | Hatchet worker | `worker-A-<run_id>` |
| Child B | Hatchet worker | `worker-B-<run_id>` |

`multiprocessing.set_start_method("spawn")` is used so each child gets a clean Python interpreter (required because the SDK uses asyncio internally).

---

## Key implementation points

| Requirement | How it's met |
|---|---|
| `sticky=StickyStrategy.SOFT` | Set on `hatchet.workflow(name=..., sticky=StickyStrategy.SOFT)` in every worker process |
| DAG `step_a → step_b → step_c` | `parents=[step_a]` on step_b, `parents=[step_b]` on step_c |
| Two distinct worker processes | `multiprocessing.Process(target=_run_worker, ...)` × 2 with `worker-A-<run_id>` and `worker-B-<run_id>` |
| Log format | `f"step={step_name} worker_id={worker_id} hostname={hostname} pid={pid}"` with `fsync` |
| Trigger once, wait | Runner uses `admin.run_workflow(...)` then `ref.result()` (blocking poll) |
| `/tmp/result.json` | Written after workflow completes: `{"worker_ids": [id_a, id_b, id_c]}` |
| No server override | No `HATCHET_CLIENT_HOST` is set; SDK uses its default (Hatchet Cloud) |
| `HATCHET_CLIENT_TOKEN` | Read automatically by the SDK from the environment |
| Worker-id source | Task output dict `{"worker_id": ...}`; log file used as fallback |
| Worker startup wait | 20 s sleep before triggering gives workers time to register |
| Clean shutdown | `proc.terminate()` + `proc.join(timeout=10)` + `proc.kill()` if needed |
