# Hatchet Task Retries with Exponential Backoff (Python SDK) ## Background Hatchet is a distributed task queue and durable execution engine. One of its core reliability features is automatic retry of failed tasks with optional exponential backoff. In this task, you will build a small Python program that defines a `flaky_task` configured to retry on failure with exponential backoff, runs the task on Hatchet Cloud, and writes the final successful result to disk. The task uses the managed Hatchet Cloud control plane (the default server endpoint baked into the SDK). Do **NOT** configure a custom `HATCHET_CLIENT_HOST_PORT`, `server_url`, or any other server-address override. ## Requirements * Use the `hatchet-sdk` Python package to define a task named `flaky_task` with the following retry configuration: * `retries=3` * `backoff_factor=2` * `backoff_max_seconds=10` * `flaky_task` must persist a cross-invocation attempt counter to the file `/tmp/attempts.txt`: * On every invocation (initial run **and** every retry), the task body reads the current attempt count from `/tmp/attempts.txt` (treat a missing file as `0`), increments the counter by `1`, and writes the new value back to `/tmp/attempts.txt` before deciding success/failure. * If the new attempt value is less than `3`, the task **MUST** raise an exception so Hatchet retries it. * If the new attempt value is `3` or greater, the task **MUST** return a JSON-serializable result containing exactly the fields `status` (string, value `success`) and `attempt` (integer, the current attempt number). * Write a runner script that: 1. Reads `ZEALT_RUN_ID` from the environment. 2. Ensures `/tmp/attempts.txt` does not exist before starting (delete it if present) so the attempt counter begins at `0`. 3. Creates a Hatchet worker whose worker name is `task-retries-worker-${ZEALT_RUN_ID}`, registers `flaky_task` on it, and starts it in the background (e.g. a thread or subprocess) so the task can be executed. 4. Triggers exactly one run of `flaky_task` with input `{}` against Hatchet Cloud and waits for the run to complete. 5. Writes the final task output (the dict returned by the successful attempt) to `/tmp/result.json` as valid JSON. 6. Shuts down the worker cleanly and exits with code 0. * The retry behavior must come from Hatchet's built-in retry policy, not from in-task `try/except` loops or any user-side retry wrapper. * The result must come from an actual Hatchet Cloud task run (no mocking, no local function-call shortcut). ## Implementation Hints * Authentication uses the `HATCHET_CLIENT_TOKEN` environment variable, which is already set in the environment. Do **NOT** hardcode any token value. * Do **NOT** set a server address. The default endpoint configured in the SDK points at Hatchet Cloud; leave it alone. * Refer to the Hatchet retry documentation for the exact decorator keyword arguments (`retries`, `backoff_factor`, `backoff_max_seconds`) on `@hatchet.task(...)`. * A typical Python program defines `hatchet = Hatchet()`, decorates a function with `@hatchet.task(...)`, creates a worker via `hatchet.worker(...)` with the task in its workflow list, and starts the worker.
