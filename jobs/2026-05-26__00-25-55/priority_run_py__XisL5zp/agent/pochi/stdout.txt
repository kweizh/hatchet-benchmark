# Hatchet Python Priority Queue Reordering ## Background Hatchet supports per-run priorities so that high-priority work can jump ahead of lower-priority work waiting in the same task's queue. You are given an isolated Python project and must demonstrate priority-based reordering by enqueuing several runs of a single task against a worker that has only one execution slot. This task targets Hatchet Cloud. The standard `HATCHET_CLIENT_TOKEN` environment variable is already set, so the SDK will use the default Hatchet Cloud server address without further configuration. ## Requirements * Define a single Hatchet Python task named `prio-task-${ZEALT_RUN_ID}` (with `ZEALT_RUN_ID` read at runtime from the environment) with a workflow/task-level `default_priority` of `1` (low). * The task body must: 1. Read the effective priority of the current run from the context (or input). 2. Compute the current epoch time in milliseconds (integer). 3. Append exactly one line to the log file (see Acceptance Criteria) in the format `<priority> <epoch_ms>\n`. 4. Sleep for approximately 2 seconds. 5. Return successfully. * Configure the worker with `slots=1` so that at most one run executes at a time and the rest queue. * Provide a runner that: 1. Truncates (creates fresh) the log file. 2. Starts the worker (e.g., in a background process/thread). 3. Submits 5 task runs back-to-back with no waiting between submissions: * First: 3 runs at priority `1` (low). * Then: 2 runs at priority `3` (high). 4. Waits for all 5 runs to complete (synchronously block until done). 5. Stops the worker cleanly and exits. * The end-to-end execution must be triggered by a single shell command. ## Implementation Hints * Install the `hatchet-sdk` Python package. * Look up Hatchet's priority API for Python: setting `default_priority` on the task/workflow definition and overriding it via the `priority` argument on `.run()` / `.run_no_wait()` invocations. Priority values are integers `1`, `2`, or `3` (or use the `Priority` enum). * Use the worker's `slots` parameter to constrain concurrency to 1. * Use `run_no_wait()` to enqueue without blocking, collect the returned references, and later resolve them to wait for completion. * Use Python's `time.time_ns() // 1_000_000` or `int(time.time()*1000)` for epoch milliseconds. * Suffix Hatchet resource names (task/workflow name) and the log path with the `ZEALT_RUN_ID` value to avoid collisions across concurrent runs of this evaluation. * The Hatchet client typically needs to be created at module load using `Hatchet()`. ## Acceptance Criteria * Project path: `/home/user/myproject` * Log file: `/tmp/prio_log_${ZEALT_RUN_ID}.txt` where `${ZEALT_RUN_ID}` is the value of the `ZEALT_RUN_ID` environment variable. * Job command: `bash /home/user/myproject/run.sh` — running this single command must perform the full end-to-end flow (start worker, submit 5 runs, wait, exit) and must terminate within \~60 seconds. * The log file must exist after the job completes and must contain exactly 5 non-empty lines. * Each line must match the format `<priority> <epoch_ms>` where `<priority>` is `1` or `3` and `<epoch_ms>` is a positive integer. * The 5 lines must contain exactly 3 entries with priority `1` and exactly 2 entries with priority `3`. * Priority reordering requirement: among lines 2 through 5 (i.e., excluding the very first executed run, which may have been a priority-1 run that was already executing when the priority-3 runs arrived), every priority-`3` line must appear before every priority-`1` line. * The Hatchet task/workflow name registered with Hatchet Cloud must be `prio-task-${ZEALT_RUN_ID}`.
